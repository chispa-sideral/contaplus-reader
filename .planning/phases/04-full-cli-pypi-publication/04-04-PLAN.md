<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Developer machine → GitHub | git push; SSH or HTTPS authenticated by Marc's credentials |
| GitHub Actions → PyPI | OIDC trusted publishing; short-lived token generated at runtime; never stored |
| GitHub Actions → TestPyPI | Same OIDC mechanism; separate pending publisher entry |
| PyPI → public internet | Published package is permanently public; cannot be deleted (only yanked) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-12 | Information Disclosure | pii-test-data/ pushed to public repo | mitigate | Task 1 runs `git status --short` and blocks push if pii-test-data/ appears; .gitignore already verified in Plan 02 |
| T-04-13 | Elevation of Privilege | PSR creates GitHub Release (which triggers publish workflow) | accept | PSR is running as Marc on Marc's machine with Marc's GitHub credentials; release creation is an intentional authorized action |
| T-04-14 | Information Disclosure | Stored PyPI token | mitigate | OIDC trusted publishing removes the token entirely; human checkpoint explicitly instructs Marc NOT to create/store a PyPI API token |
| T-04-15 | Tampering | Unintended version bump by PSR scanning old commits | mitigate | Task 3 requires `semantic-release version --print` dry-run before the real run; stop-and-investigate if version != 0.1.0 |
| T-04-16 | Denial of Service | Accidental publish of broken wheel | mitigate | D-05 TestPyPI dry-run (testpypi job) gates the pypi job; if TestPyPI upload or page render fails, pypi job is blocked |
| T-04-SC | Tampering | npm/pip/cargo installs | accept | All packages legitimacy-audited in 04-RESEARCH.md [OK]; Plan 04 adds no new package installs |
</threat_model>
