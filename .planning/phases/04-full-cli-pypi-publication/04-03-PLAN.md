ci/smoke.mjs pattern — use RESEARCH.md § "Pattern 5: micropip smoke test" verbatim:
  import { loadPyodide } from "pyodide";
  async function main() {
    const pyodide = await loadPyodide();
    await pyodide.loadPackage("micropip");
    const micropip = pyodide.pyimport("micropip");
    await micropip.install("contaplus-reader");   // or process.env.WHEEL_URL for local testing
    await pyodide.runPythonAsync(`
      import contaplus_reader
      from contaplus_reader import read, ContaPlusReadError
      print("contaplus-reader imported successfully")
    `);
    console.log("Smoke test PASSED");
  }
  main().catch((e) => { console.error(e); process.exit(1); });

Key finding from RESEARCH.md D-09: micropip.install("contaplus-reader") triggers micropip's internal loadPackage("pandas") call — no manual pre-load of pandas/numpy needed. See RESEARCH.md Assumptions Log A1 for the optional safety-belt pattern.

Local wheel variant (RESEARCH.md lines 424–432): the workflow can serve dist/*.whl via python3 -m http.server 8080 if the package does not yet exist on PyPI. Include a conditional in smoke.mjs:
  const wheelUrl = process.env.WHEEL_URL;
  const packageRef = wheelUrl || "contaplus-reader";
  await micropip.install(packageRef);
This makes the smoke test usable both locally (before PyPI) and in CI (after PyPI publish).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → PyPI | OIDC short-lived token exchanged at runtime; no stored secret |
| GitHub Actions runner → TestPyPI | Same OIDC mechanism; separate pending-publisher entry on test.pypi.org |
| ci/smoke.mjs → PyPI / Pyodide CDN | npm fetch for pyodide package; micropip fetches wheel from PyPI; all over HTTPS |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-07 | Information Disclosure | Stored PyPI token | mitigate | OIDC trusted publishing — no token ever stored in secrets or workflow (per D-06). id-token: write at job level only (Pitfall 1). |
| T-04-08 | Tampering | Wheel tampered in CI artifact | mitigate | uv publish with OIDC attestation enabled by default; PyPI stores Sigstore attestation metadata alongside the wheel |
| T-04-09 | Tampering | workflow-level id-token: write grants OIDC to all jobs | mitigate | Acceptance criterion explicitly requires id-token: write at JOB level only (testpypi + pypi); build and micropip-smoke have no write permissions |
| T-04-10 | Tampering | release.yml uses unpinned action versions | accept | actions/checkout@v5, astral-sh/setup-uv@v6, actions/setup-node@v4 are the current major versions; SHA-pinning is a hardening step deferred to v2 |
| T-04-11 | Information Disclosure | pii-test-data/ in GitHub push | mitigate | .gitignore verification done in Plan 02 Task 2; this plan adds no new files that could bypass gitignore |
| T-04-SC | Tampering | npm install pyodide in CI | accept | pyodide npm package legitimacy confirmed [OK] in 04-RESEARCH.md Package Legitimacy Audit; 6-year-old package from pyodide/pyodide org |
</threat_model>
